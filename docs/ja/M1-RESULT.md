# Milestone 1: PoC の結果

`discover → understand → choose → follow → record` が成立するかを確かめた。
成立した。ただし **Semantic Audit にはもう一つ前提が要る**ことが分かった。

## 何を作ったか

| | |
| --- | --- |
| Semantic Browser | 本リポジトリ。`walker.py` / `decision.py` / `main.py` |
| 意思決定エンジン | [Laya-MLX](./laya-mlx.md)。文章を生成せず、提示した選択肢の確率を返す |
| 対象アプリケーション | [semantic-browser-fixture](https://github.com/koriym/semantic-browser-fixture)。査読ジャーナル（HAL + ALPS）。実装者はソースを読まず、HTTP と実行時取得の ALPS だけで書いた |

## 検証項目への答え

| `docs/PLAN.md` の問い | 答え |
| --- | --- |
| HAL と ALPS だけから、事前知識なしに遷移候補を発見できるか | **できる** |
| 一連の処理を繰り返して自律的に巡回できるか | **できる** |
| Laya が意味情報に基づいて妥当な次の一手を選択できるか | **条件付き。下記** |

3 番目は単純な yes/no にならなかった。同じ 7 ホップの課題で、条件を変えると
成績が 3/7 から 5/7 まで動く。動かしているのは主に**記述がエンジンに届いて
いるか**であって、エンジンの賢さではない。

- ALPS の `doc` が日本語で、英語チェックポイントを使うと非 ASCII が落ちる。
  実質 `title` だけで判断することになり 3/7
- 同じ記述を多言語チェックポイントに渡すと 5/7
- コレクションの項目は、その集合の rel に descriptor がないと意味の経路を持たない

通しで走らせると 1 歩目で外れる。選んだ候補の記述にはこう書いてある。

> 査読を依頼できる人の名簿を開く。**特定の原稿の査読者を探す用途には使えない。**

## エンジンについて再現した性質

いずれも決定的（同一入力 5 回で完全一致）。モデルの揺らぎではない。

| | |
| --- | --- |
| **否定を読まない** | 「〜には使えない」と書かれた候補を 0.82、「まだ掲載されていない」を 0.79 で選ぶ |
| **確率は候補集合に依存する** | 無関係に見える候補を 1 つ外すと勝者が入れ替わる（0.627 → 0.601 で逆転） |
| **確信度は正しさと対応しない** | 誤答を 0.96、正答を 0.29 で返す |
| **state に URI を書くと選択が壊れる** | ラベルと経路の表層一致。記述を書き換えても直らない |

最後の一点は README の *"follows meaning, not routes"* が方針であると同時に
**動作条件**であることを意味する。

これらはモデル固有の欠陥ではなく、**cross-encoder による reranking という
種類の既知の性質**である（[docs/laya-mlx.md](./laya-mlx.md)）。分類名を
先に押さえていれば、否定と候補集合依存の 2 つは予測できた。

## 既知の限界: Safety First はまだ宣言を見ていない

README は「`unsafe` なメソッドを既定では実行しない」と述べているが、
実装が見ているのは HAL のリンクにある `method` プロパティだけである
（`walker.py`）。

**HAL に `method` プロパティは存在しない。** その分岐が働いているのは、
本 PoC の対象アプリがそれを出しているからにすぎない。実 API に向ければ
何も濾過しない。

宣言された安全性は ALPS の `type`（`safe` / `idempotent` / `unsafe`）にあり、
コードはこれをどこでも読んでいない。そして **ALPS の `type` と実際の
HTTP メソッドが一致しているか**は、上で「決定的で今すぐ使える」と書いた
Consistency 検査そのものである。実装はその片側しか見ていない。

## Semantic Audit に足りない前提

自己記述性を測るには、計器が**よく記述されたものとそうでないものを分けられる**
ことを先に示さなければならない。それができていない。

実アプリの ALPS で試した。BEAR.Sunday で書かれた EC アプリのプロファイル
（100 状態 / 208 遷移）である。**このアプリは起動していない。** データベースを
要するため、`alps.json` だけを対象にした。巡回は行っていない。

各遷移の `title` を問いにして、兄弟の `doc` の中から自分を引けるかを
`laya-multilingual-mlx`（322M）で測り、余白 0.10 未満を「紛らわしい対」として
挙げた。48 件出た。

しかし内容を読むと成立していない。

```
goShoppingError  safe    在庫不足、決済失敗などのエラー発生時にリダイレクトされる
doCheckout       unsafe  税計算・送料計算・在庫引当・ポイント減算を実行し決済確定
```

**正反対の 2 つ**が margin −0.90 で「区別できない」と出る。測っていたのは
記述の曖昧さではなく、322M encoder の照合能力だった。

この計器では `アプリの記述が曖昧` と `エンジンが読めない` を分離できない。
**校正されていない計器で他人のコードを採点してはならない。**

## 計器に依存しない監査は機能する

同じ ALPS に対する集合演算だけの検査は、サーバーを起動せずに走り、
結果が決定的で、エンジンの性能に左右されない。

| 検査 | 結果 |
| --- | --- |
| `doc` / `title` / `rt` の欠落 | 208 遷移すべて完備。**ゼロ** |
| どの状態からも提示されない遷移 | **44 / 208** |
| 入ってくる遷移が 1 つもない状態 | **15 / 100** |

後者 2 つは「宣言の集合に経路が存在しない」という主張であり、
**どのエンジンを使っても到達できない。** 測定ではなく構造である。

（入口を `Top` に限ると「到達不能 66」と出るが、管理画面は `AdminLogin` を
別の入口として持つ。入口の集合を取り違えると、設計どおりの分離を欠陥と
report してしまう。）

## この PoC の結論

**ブラウザは成立した。監査は、決定的な部分だけが今すぐ使える。**

意味に基づく判定を監査に使うには、先に計器の校正が要る。
既知の良い記述と既知の悪い記述を用意し、計器がそれを分離することを
示してから、未知のアプリに向ける。それが Milestone 3 の前に入る。

## 作業上の教訓

この PoC で最も繰り返した誤りは、モデルの失敗でも実装の失敗でもなく、
**計器の性質を対象の性質として読むこと**だった。7 回起きた。

- 候補に正解を含めたまま制約の効果を確かめた
- state に答えの語を残したまま成績を評価した
- ゴール文にデータと同じ語を入れたまま成績を評価した
- 記述をエンジンに見せずに「意味を解釈できない」と結論した
- ページに存在しない事実について「到達したか」を問うた
- 候補の記述をそのまま問いにして、文字列の同一性を測った
- 正反対の記述を「紛らわしい」と report しかけた

いずれも**判別されなくても済む形でテストを組んでいた**。
自己記述性の監査という主題そのものが、同じ規律を要求する。
